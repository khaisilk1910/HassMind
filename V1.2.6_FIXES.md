# HassMind v1.2.6 — Telegram Integration, Custom API Actions & Rich Zalo Formatting

## 1. Telegram is a first-class Web Admin Integration

- Telegram now appears under **Web Admin -> Integrations**.
- Admin can enable/disable Telegram, set the Bot Token and Allowed Chat IDs without editing the Docker stack.
- Runtime Bot Token is stored as `/data/secrets/integration_telegram_bot_token` and is never returned by the API.
- A supervisor watches the effective Telegram configuration and restarts polling when it changes, so normal Web Admin edits do not require a container restart.
- Integration health calls Telegram Bot API `getMe`, exposing missing/invalid token and connectivity problems in the Integration Status panel.
- `setup.sh` migrates the legacy `secrets/telegram_bot_token.txt` once when the runtime secret does not already exist.

## 2. Custom HTTP Integrations can expose API functions

A Custom Integration can now define fixed **API Actions / Agent Tools**. An action declares:

- action ID/name/description;
- enable flag;
- explicit Agent opt-in (`agent_enabled`);
- fixed HTTP method: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`;
- fixed relative path, optionally with declared path parameters such as `/api/device/{device_id}`;
- `read` or `write` mode;
- request target (`auto`, `query`, `json`);
- JSON Schema for model-supplied arguments.

Only enabled actions with `agent_enabled=true` are exposed as LLM tools. The model cannot supply an arbitrary URL, HTTP method, header name or path. This intentionally avoids a generic HTTP tunnel.

`read` actions may participate in parallel read-only tool batches. `write` actions are treated as mutating operations and are not parallelized with read-only batches. Enabling a custom write action for the Agent is an operator opt-in; v1.2.6 does not add a separate human-approval workflow for arbitrary Custom Integration actions.

Example read action:

```json
[
  {
    "id": "device-status",
    "name": "Device status",
    "description": "Read one device status",
    "enabled": true,
    "agent_enabled": true,
    "method": "GET",
    "path": "/api/devices/{device_id}",
    "mode": "read",
    "request_target": "auto",
    "input_schema": {
      "type": "object",
      "properties": {
        "device_id": {"type": "string", "description": "Device identifier"}
      },
      "required": ["device_id"],
      "additionalProperties": false
    }
  }
]
```

For a `POST` action, `request_target: "auto"` sends remaining arguments as JSON. For `GET`/`DELETE`, `auto` sends remaining arguments as query parameters.

## 3. Zalo rich-text dialect

Outgoing Zalo responses now preserve the syntax supported by the configured Zalo Server instead of stripping all Markdown. HassMind supports/normalizes:

- `#` / `##` / `###` / `####`-`######` headings;
- `**bold**`, `*italic*`, `***bold+italic***`;
- `__underline__`, `~~strike~~`, single-backtick inline text;
- blockquotes and Markdown links;
- `{red}`, `{orange}`, `{yellow}`, `{green}`, `{big}`, `{small}` tags;
- unordered/ordered lists and up to 8 spaces of indentation.

Unsupported model constructs are normalized before delivery:

- Markdown tables become readable bullet rows;
- fenced code blocks lose the unsupported fence but keep their content;
- Markdown horizontal rules become a Unicode separator;
- `<FollowUp .../>` becomes a supported green suggestion line;
- unsupported raw HTML/XML and unknown brace tags are removed.

The Zalo-specific system prompt asks for concise mobile formatting and uses green for normal/healthy state, orange for attention/unavailable state, and red only for warnings/errors.

## 4. Compatibility

- Existing SQLite data is retained. Startup adds the `actions_json` column to older `custom_integrations` tables when needed.
- Existing Custom Integrations remain valid and simply start with no API Actions.
- Camera TTS, FaceDetect, Zalo, Wyoming and HA Custom Components behavior remains compatible.
